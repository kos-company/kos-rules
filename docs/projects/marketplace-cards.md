# Проект: карточки товаров на маркетплейсах (WB, Ozon, ЯМ)

Общие правила — [00_ПРОЧИТАЙ_СНАЧАЛА](https://kos-company.github.io/kos-rules/read-first.html).

## Цель
Карточки без ошибок фактов, находимые по запросам покупателей, понятные покупателю. Массовое обновление пакетами.

## Порядок анализа товара (от дешёвого и точного к дорогому)
0. Выбор: реестр товаров по выручке МП и доле МП в продажах. Начинаем сверху.
1. Есть ли что продавать и выгодно ли: остатки, продажи, экономика. Нет остатка или минус — карточку не трогаем, сообщаем.
2. Не врёт ли карточка: сверка с ТХ/паспортом (размеры, материалы, комплект, артикулы, запрещённые формулировки).
3. На что жалуются покупатели: отзывы, вопросы, причины возвратов.
4. Находят ли: ключи, название, описание, позиции.
5. Убеждает ли: фото, инфографика, воронка (показы → переходы → корзина → заказ).
6. Оформление: категория, обязательные характеристики, документы.
7. Цена против конкурентов (решает руководитель).
8. Заливка и замер через 7–14 дней с контрольной группой.
Не менять всё сразу: иначе не понять, что сработало.

## Правила текстов
Действуют только для текстов карточек маркетплейсов (и, по решению владельца, сайта) по изделиям КОС. В другие проекты не переносить.
- Факты об изделии — только из ТХ, паспорта, инструкции, техдокументации. Документ относится к модели, только если артикул указан ВНУТРИ документа; папка или имя файла это не подтверждают.
- Противоречие между документами — не выбирать самому, вынести вопрос человеку; спорный факт в текст не включать.
- Медицинские формулировки : МОЖНО описывать, кому и в какой ситуации удобно изделие — пожилые, маломобильные, люди с инвалидностью, лежачие; после операции, травмы или болезни; слабость в ногах; трудно вставать и пересаживаться; помощь ухаживающему, родственникам, сиделке. НЕЛЬЗЯ обещать медицинский эффект (лечит, восстанавливает, реабилитация, профилактика, снижает спастику), указывать диагнозы как показание, называть изделие медицинским или реабилитационным средством. Названия конкретных болезней — только по отдельному решению владельца.
- Никогда не писать: «загрязнение биологическими или химическими веществами», «изделие не предназначено для лечения» и аналоги.
- Ключи: ключи из ядра компании (лист «Ядро») брать всегда, если не запрещены; нет частоты — «нет данных», не выбрасывать. Частоты подписывать по источнику.
- Название начинается с типа товара; отличие модели — в названии и первом абзаце. Без артикулов, без набора синонимов.
- Структура описания: сценарий → конструкция → материалы → подбор размера → как пользоваться → безопасность → уход. Что не влезло в характеристики — раскрыть в описании.
- Дубли ключей между столбцами таблицы ключей допустимы.
- Количества: «Вертикальных ручек — 3, горизонтальных — 4».
- Подробный промпт: таблица текстов, лист «Промпт для ответственного за тексты».

## Данные проекта
- Площадки (WB, Ozon, ЯМ) — один общий сборщик (только чтение) раз в день, выгрузки в закрытой папке проекта, доступ у руководителя. В API самим не ходить: у площадок общие лимиты запросов на кабинет.
- Документы изделий — по ссылкам из задач Битрикса (группа «Разработка, цех-1, тех.части»).
- Спрос — SellerStats, аналитика поиска WB, свои запросы Ozon, Wordstat; ядро ключей — лист «Ядро».
- 1С — выгрузки отчётов в «Данные/1С/<дата>».

## Владельцы полей карточек
См. 02_РОЛИ_И_ВЛАДЕЛЬЦЫ, раздел «Карточки». Чужое поле не править — через «Очередь правок».

## Заливка
- Пакет утверждает ответственный за тексты, заполняя «кто утвердил» и «дата». ЯМ/Ozon — «Предпросмотр» → «Записать». WB — «Сделать Excel для WB», загрузку выполняет ответственный сотрудник. Запись через API — только по отдельно согласованному порядку проекта.
- Excel-пакет собирается из СВЕЖЕЙ выгрузки непосредственно перед загрузкой: иначе затрутся чужие правки (фото и т.п.).
- Перед заливкой — снимок «до» для отката. После — проверка через 1–2 ч и 24 ч.
- Ozon в категории «Одежда» показывает покупателю автоматическое название — название там не меняем.
- ЯМ может подтягивать данные с других площадок через интеграцию — проверить настройки, чтобы заливка не откатывалась.

## Запись через API и бэкапы
- Отвечает тот, кому поручена работа с карточками (02_РОЛИ_И_ВЛАДЕЛЬЦЫ, «Запись через API и бэкапы»); временно — ответственный за правила. Роль передаётся вместе с этим разделом и заданием на бэкапы.
- Без выполнения требований этого раздела запись через API не запускается. Бэкап, из которого ни разу не восстанавливали, считается отсутствующим.
- Каждая запись — строка в «Журнал изменений карточек». Копии бэкапов — не только на компьютере писателя (3 копии, 2 места, 1 вне ПК); персональных данных в бэкапах карточек нет и быть не должно.
- Записывай только утверждённый пакет. Сверь свежие карточки и сохрани снимок ДО. Проверь предпросмотр и отпечаток пакета перед записью. Удаление карточек, склейка, расклейка и смена категории через писатель запрещены.
- Лимит пакета — 50 SKU. Больше — только с отдельным подтверждением. Цена меняется по отдельному согласованному процессу. При отклонении от текущей цены больше настроенного порога (по умолчанию 10%) остановись. Текущий писатель меняет только тексты.
- Сборщик сохраняет сжатые снимки карточек с текстами, характеристиками, ценами и ссылками на фото. Хранение — ежедневно за 90 дней, далее по одному полному снимку в неделю. Сами фото сохраняются еженедельно. Копия вне ПК — по решению владельца.
- Раз в месяц проверь восстановление текстов на согласованном тестовом SKU. Выбери дату снимка, сверь предпросмотр, запиши только после одобрения. Проверь результат и верни исходный текст. На Ozon писатель восстанавливает аннотацию.



В кабинеты через браузер не заходи, даже по прямой просьбе. Объясни, какой кнопкой программы выполняется действие.
